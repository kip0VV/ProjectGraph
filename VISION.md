# ProjectGraph

## 1. Что такое ProjectGraph

**ProjectGraph** — долгосрочный проект для анализа структуры программных проектов с помощью графов и методов дискретной математики.

Основная идея:

> Пользователь передаёт ProjectGraph свой программный проект. ProjectGraph исследует его структуру, превращает найденные связи в графовую модель, анализирует её и позволяет человеку визуально исследовать архитектуру проекта.

ProjectGraph должен помогать отвечать не только на вопрос:

> «Какие файлы есть в проекте?»

но прежде всего:

> «Как этот проект устроен и как его части связаны между собой?»

---

## 2. Главный принцип

В основе ProjectGraph находится преобразование:

**исходный код → математическая модель → анализ → визуальное представление**

Например, программный проект:

```text
main.cpp
user.cpp
database.cpp
logger.cpp
```

может быть представлен графом, где:

- вершины — элементы проекта;
- рёбра — связи между ними.

Если `main.cpp` зависит от `user.cpp`, появляется ориентированное ребро:

```text
main.cpp → user.cpp
```

Весь проект превращается в граф:

```text
main
 ↓
user
 ├────→ database
 │          ↓
 └──────→ logger
```

После этого ProjectGraph может применять алгоритмы и математические свойства графов для исследования архитектуры.

---

## 3. Что ProjectGraph должен анализировать

На ранних этапах основной объект анализа — **файлы и зависимости между файлами**.

В дальнейшем уровень анализа может становиться глубже:

```text
Project
   ↓
Directories
   ↓
Modules
   ↓
Files
   ↓
Classes
   ↓
Functions
```

Один программный проект потенциально может порождать несколько разных графов.

Например:

**Dependency Graph**

```text
File A → File B
```

**Class Graph**

```text
UserService → Database
```

**Call Graph**

```text
login()
   ↓
validatePassword()
   ↓
createSession()
```

**Git/Change Graph**

```text
User.cpp ←→ Session.cpp
```

где связь показывает, что файлы часто изменяются вместе.

ProjectGraph не обязан поддерживать всё это сразу. Это направления возможного развития.

---

## 4. Что должен уметь ProjectGraph

Главная задача — не просто нарисовать красивую схему проекта.

ProjectGraph должен **анализировать структуру**.

В перспективе он сможет исследовать:

- прямые зависимости;
- косвенные зависимости;
- пути между компонентами;
- циклические зависимости;
- компоненты связности;
- сильно связанные компоненты;
- критические вершины и связи;
- количество входящих и исходящих зависимостей;
- центральные компоненты системы;
- изолированные части проекта;
- структуру модулей;
- изменение архитектуры со временем;
- зависимости, появившиеся после изменения кода.

Например:

```text
Circular dependency:

User
 ↓
Session
 ↓
Database
 ↓
User
```

Или:

```text
Why does API depend on Database?

API
 ↓
UserService
 ↓
Repository
 ↓
Database
```

То есть ProjectGraph должен позволять **исследовать причины связей**, а не только показывать их наличие.

---

## 5. Визуализация

Одна из центральных частей конечного продукта — интерактивное представление архитектуры.

Пользователь должен иметь возможность увидеть проект примерно как сеть:

```text
              Auth
             /    \
            ↓      ↓
          User   Session
            \      /
             ↓    ↓
             Database
                 ↓
               Logger
```

В будущем желательно иметь возможность:

- приближать и отдалять граф;
- выбирать вершину;
- смотреть её зависимости;
- скрывать ненужные типы связей;
- переходить между уровнями `Project → Module → File → Class → Function`;
- подсвечивать найденные пути;
- подсвечивать циклы;
- отображать результаты алгоритмов;
- сравнивать состояние архитектуры в разные моменты времени.

Визуализация должна быть способом **понять результаты анализа**, а не просто декоративной частью программы.

## 6. Где здесь дискретная математика

ProjectGraph рассматривает программный проект как дискретную структуру.

Множество компонентов:

\[
V = \{v_1,v_2,\ldots,v_n\}
\]

Множество отношений между ними:

\[
E \subseteq V \times V
\]

Получаем граф:

\[
G=(V,E)
\]

Поэтому знания дискретной математики должны постепенно становиться инструментами ProjectGraph.

В проекте потенциально применяются:

- множества;
- бинарные отношения;
- ориентированные графы;
- неориентированные графы;
- взвешенные графы;
- пути;
- циклы;
- связность;
- деревья;
- DAG;
- компоненты связности;
- strongly connected components;
- степени вершин;
- топологическая сортировка;
- мосты;
- точки сочленения;
- различные характеристики и метрики графов.

Новые изученные математические темы могут становиться новыми возможностями ProjectGraph, если они действительно помогают анализировать программные проекты.

## 7. Образовательная цель

ProjectGraph — не только конечный продукт.

Это проект, который должен **расти вместе с моими знаниями**.

Я не должен сначала изучить весь C++, алгоритмы и дискретную математику, а потом начать ProjectGraph.

Процесс должен выглядеть наоборот:

```text
хочу реализовать новую возможность
             ↓
не хватает знаний
             ↓
определяю, чего именно не знаю
             ↓
изучаю эту тему
             ↓
реализую её самостоятельно
             ↓
ProjectGraph становится сложнее
             ↓
возникает следующая проблема
```

Поэтому простота первых версий является нормальной частью проекта.

---

## 8. Принцип разработки

ProjectGraph не должен превращаться в проект, большую часть которого написал AI и который я сам не понимаю.

Основной принцип:

> Я должен понимать код, который становится частью проекта.

AI можно использовать для:

- объяснения неизвестных концепций;
- поиска ошибок;
- обсуждения архитектуры;
- code review;
- объяснения алгоритмов;
- поиска возможных подходов;
- изучения C++;
- изучения дискретной математики.

Но сложность проекта должна увеличиваться вместе с моими собственными знаниями.

---

## 9. Что ProjectGraph НЕ обязан быть

ProjectGraph не обязан оставаться исключительно:

- C++-программой;
- учебным проектом;
- анализатором только C++;
- программой только про графы;
- консольным приложением;
- desktop-приложением;
- статическим анализатором;
- инструментом только для одного человека.

Технологии и форма конечного продукта могут изменяться.

Неизменной пока остаётся центральная идея:

> **исследовать устройство программных проектов через их структуру и взаимосвязи.**

---

## 10. Критерий для новых идей

Когда появляется новая функция, библиотека, технология или направление, нужно задать три вопроса:

**1. Какую проблему ProjectGraph это решает?**

Если конкретной проблемы нет, возможно, функция добавляется просто потому, что технология кажется интересной.

**2. Помогает ли это лучше понять структуру программного проекта?**

Если да — идея хорошо соответствует первоначальному направлению.

**3. Хочу ли я сам изменить направление ProjectGraph?**

Ответ на первые два вопроса не является запретом.

Это мой личный проект.

Я могу сознательно изменить его назначение, архитектуру или вообще превратить ProjectGraph во что-то другое.

Первоначальная концепция нужна только для того, чтобы такие изменения происходили **осознанно**, а не случайно.

# Точка старта

На момент создания ProjectGraph мои знания C++ ещё небольшие.

Поэтому первая версия не пытается анализировать настоящий исходный код.

Мы начинаем с фундаментальной модели:

```text
файл = вершина
зависимость = ориентированное ребро
```

Первая задача:

> Научиться представлять небольшой граф зависимостей в памяти программы и работать с ним.

Дальнейшие возможности будут добавляться постепенно по мере появления необходимых знаний.

# Долгосрочное направление

В наиболее развитом виде ProjectGraph можно представить так:

```text
                 PROGRAMMING PROJECT
                         │
                         ▼
                       SCAN
                         │
                         ▼
                      PARSER
                         │
                         ▼
                STRUCTURAL MODEL
                         │
                         ▼
                    GRAPH MODEL
                         │
          ┌──────────────┼──────────────┐
          ▼              ▼              ▼
      Algorithms     Mathematics     Git history
          │              │              │
          └──────────────┼──────────────┘
                         ▼
                      ANALYSIS
                         │
                         ▼
                  VISUALIZATION
                         │
                         ▼
                     DEVELOPER
```

Главная ценность ProjectGraph:

> **превращать сложную кодовую базу в структуру, которую человек может исследовать, анализировать и понимать.**
